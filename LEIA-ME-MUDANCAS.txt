=== Pediu Chegou — Mudanças aplicadas ===

1. Nome: "Pediu Chegou" (login, topo, título, console).
   (Nota: em pt-BR o correto seria "Pediu Chegou" — o nome foi mantido como solicitado.)
2. Cores: mantidas (ainda não definidas).
3. Quantidade: botões +/− ao lado de cada produto no cardápio.
4. Lojas: podem enviar foto de cada produto (prato/bebida/sobremesa); aparece no cardápio.
5. Entregador: foto do rosto obrigatória no cadastro (sem óculos/boné/chapéu).
   Perfil público (nome + foto) visível ao cliente no pedido.
6. Entregador: CPF, nome, sobrenome e nome social (opcional, abaixo do nome).
7. Cadastro do entregador em 3 etapas com botão "Próximo":
   - Etapa 1: dados pessoais + foto do rosto + e-mail.
   - Etapa 2: bicicleta (nº, cor, aro 24/26, elétrica sim/não — editável quando quiser sem autorização)
     ou moto (CNH dos dois lados — provisória vale —, documento da moto, RENAVAM, e dados pré-preenchidos:
     marca, modelo, cor, cilindrada).
   - Etapa 3: usuário (CPF ou e-mail), senha (mín. 8 caracteres: 2 números, 1 maiúscula, 5 minúsculas),
     termos e condições. Senha NÃO pode ser CPF/data de nascimento/RENAVAM — aviso na hora, sem penalidade.
   - Confirmação de e-mail por código de 6 dígitos (reenviável). Em modo demo o código aparece na tela
     e no console do servidor (em produção, integrar SMTP/SendGrid).
   - Cadastro vai para revisão do administrador (aprovado/rejeitado no painel admin, com foto e documentos).
8. Pagamentos: apenas Pix e Dinheiro — cartões de crédito/débito removidos.
9. Fluxo do pedido:
   - Cliente confirma → loja recebe agora (aceitar ou recusar), não espera.
   - Loja aceita → entregador mais próximo (por GPS) vê o pedido e pode aceitar imediatamente
     (não espera a loja marcar "pronto").
   - Entregador aceita → botões de GPS: Waze (se tiver instalado abre o app) ou Google Maps até a loja.
   - Botão "Cheguei na loja" aparece automaticamente quando o GPS detecta ≤100 m da loja.
   - Na loja: entregador informa o Nº do pedido. Quando pronto, botão "Coletar pedido" com confirmação
     IRREVERSÍVEL (não volta atrás). Gera código de coleta (2 códigos: Nº do pedido + código de coleta);
     a loja vê o código de coleta no painel para verificar. Responsabilidade passa ao entregador (coletado_at).
   - Depois: "Ir até o cliente" com GPS (Waze/Google).
   - Cliente tem um código pessoal cadastrado no perfil (editável quantas vezes quiser; visível só para
     cliente e admin — o entregador NÃO tem acesso). Na chegada, o cliente diz o código, o entregador digita
     e a entrega é finalizada. Código errado = não finaliza.

3. RECONHECIMENTO FACIAL DO ENTREGADOR (obrigatório em TODO login):
   - Objetivo: a conta do entregador é pessoal e intransferível — ninguém mais pode entrar
     com o login dele. Cada vez que ele se desconecta e volta a entrar, deve validar o rosto.
   - Fluxo: login do entregador → tela "Verificação facial obrigatória" → câmera aberta
     (getUserMedia, câmera frontal) → captura selfie → biblioteca face-api.js (via CDN)
     compara o rosto capturado com a foto cadastrada no ato do cadastro (distância < 0.6 = match).
     Se der match → novo token JWT com face_verified=true → entra no painel.
   - Sem validação facial, o entregador NÃO consegue: ver pedidos disponíveis, aceitar entrega,
     marcar cheguei na loja, coletar pedido, finalizar entrega, atualizar localização,
     solicitar antecipação, denunciar atraso. Todas essas rotas retornam 403.
   - 5 tentativas sem êxito → sessão encerrada e orienta a contatar o admin.
   - Contas antigas sem foto de rosto: no primeiro login após esta versão, a selfie capturada
     é cadastrada como referência (enrollment). Das próximas vezes, é comparada.
   - Fallback: se a biblioteca face-api não carregar (sem internet/CDN), a selfie ainda é
     capturada e registrada (prova de vida/liveness), com auditoria.
   - Backend: tabela nova "face_verifications" (user_id, foto capturada, match_score,
     resultado, data) + coluna users.face_verified_at. Endpoint POST /api/auth/face-verify.
     Middleware entregadorRequired = auth + role entregador + face verificado.
   - O token com face_verified=true dura a sessão/login. Ao sair (Sair) e entrar de novo,
     a validação facial é exigida novamente.

IMPORTANTE — produção:
   - Câmera só funciona em HTTPS (ou localhost). Publique o app com certificado SSL.
   - Para maior segurança, o ideal é integrar reconhecimento facial server-side
     (AWS Rekognition / Azure Face / Google Vision) — o atual compara no navegador e
     registra auditoria no servidor, suficiente para MVP.
   - O código de verificação de e-mail em produção (NODE_ENV=production) não é devolvido
     pela API — integre SMTP/SendGrid para envio real.

=== v7 — nov/2026: Versão ESCALÁVEL (PostgreSQL + Docker) ===

Por que mudou: o SQLite (v6 e anteriores) é um banco em arquivo, ótimo para começar, mas
limita a ~100-200 usuários simultâneos e não permite mais de um servidor rodando ao mesmo
tempo. A v7 trocou por PostgreSQL (o banco usado por iFood, Uber, etc.), que escala para
milhares de usuários simultâneos e múltiplos servidores por trás de um balanceador.

O que mudou no código:
- db.js: agora usa `pg` (pool de até 20 conexões) em vez de better-sqlite3.
  Todas as queries são assíncronas (async/await). Transações via BEGIN/COMMIT/ROLLBACK.
- Todas as rotas (auth, orders, stores, admin, reports, extras) convertidas para async/await.
- server.js: aguarda a inicialização do banco (esquema + seed + admin) antes de aceitar conexões.
  Se não conseguir conectar, mostra erro claro e encerra.
- package.json: dependência `pg` no lugar de `better-sqlite3`. Versão 3.0.0.
- Melhorias de SQL para escala: created_at::date = CURRENT_DATE, EXTRACT(EPOCH ...) para
  tempos de espera, SERIAL para IDs, índices mantidos.

Como rodar (3 opções):

OPÇÃO 1 — Docker (mais fácil, já sobe Postgres + app):
  docker compose up --build
  → http://localhost:3000  (admin: admin@pediuchegou.com / troque-esta-senha-123)
  Para contas de teste: descomente SEED_DEMO no docker-compose.yml.

OPÇÃO 2 — Postgres local + Node:
  1. Instale o PostgreSQL (ou use Neon/Railway/Render na nuvem).
  2. Crie o banco: createdb pediuchegou
  3. Copie .env.example para .env e ajuste DATABASE_URL.
  4. npm install && npm start → http://localhost:3000

OPÇÃO 3 — Hospedagem gerenciada (Render, Railway, Fly.io):
  - Crie um serviço PostgreSQL (Neon é gratuito e funciona).
  - DATABASE_URL vem pronto do provedor. Defina PGSSL=1 se exigir SSL.
  - Defina JWT_SECRET, ADMIN_EMAIL, ADMIN_PASSWORD. NODE_ENV=production.

Variáveis de ambiente (ver .env.example):
  DATABASE_URL (obrigatória), PGSSL, PORT, ADMIN_EMAIL, ADMIN_PASSWORD,
  JWT_SECRET (obrigatória trocar em produção), SEED_DEMO (opcional), NODE_ENV.
